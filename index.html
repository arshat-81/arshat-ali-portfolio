ai_module_migrator/README

Module Migration AI

Problem
Moving a custom module to a new Odoo version means reading every file for what changed. It is slow, and a missed rename only shows up later.
What it does
Upload a zipped module or point it at a folder on the server. It scans the code and lists what will break between your Odoo version and the target, anywhere from 11 to 20. Then it migrates file by file with the AI provider you pick: OpenAI, Gemini, Claude, Groq, DeepSeek, Ollama or any OpenAI-compatible endpoint. The static report works with no AI key at all.
Under the hood
One job per file, run by a queue I wrote for it. Jobs are claimed with FOR UPDATE SKIP LOCKED, stalled jobs are taken back, and failures retry with backoff. If the model sends back broken output, the job retries with the error attached. Paths inside uploaded zips are checked so an archive cannot write outside its folder.
Checked by
By hand on Odoo 17: upload, scan, static report, export. The AI migration needs a provider key and a running queue, so it is not under automated tests.

mdx_mcp_server/README

MCP Server & Audit

Problem
An AI assistant that can reach Odoo needs limits. Handing it one all-powerful key is how a chatbot ends up editing invoices.
What it does
Speaks the Model Context Protocol (2025-06-18) over streamable HTTP, so Claude, ChatGPT or Cursor can search and read records and, if you allow it, change them. Each tool has its own permission. A write can wait for a person to approve it, and every call is logged.
Under the hood
Calls run as the key's user, never as root, so Odoo's own access rules still apply. Sensitive fields are masked even for administrators. A dry run shows what a write would do and changes nothing.
Checked by
29 tests on Odoo 17. Among them: a write that needs approval does not write until someone approves it, and rejecting it leaves the record alone.

mdx_api_gateway/README

REST API

Problem
Odoo's own RPC answers to one global key that reaches everything its user can. Give that key to a Shopify sync and you have given it the whole database.
What it does
Each integration gets its own key and profile: which models, which fields, which operations, an optional IP allowlist, an expiry date, or OAuth client credentials. On top of that sit bulk updates, upsert by external id, grouped aggregates, import and export, background jobs, signed webhooks with retries, an OpenAPI description cut down to the profile, and an audit log.
Under the hood
Every request is checked against the profile first and Odoo's access rules second, so a profile can only narrow what a user may do. On Odoo 17 the keys have no expiry column of their own, so the gateway keeps the expiry on its own record and enforces it on every call.
Checked by
98 tests on Odoo 17, including one that makes sure an ordinary global Odoo key is refused by the gateway.

arshat_ali/tests/

How I check my work

Most of the add-ons ship with their own tests. On 25 October I moved ten of them from Odoo 18 down to Odoo 17 and ran all 355 tests together on a fresh database.

The first runs failed in places I had not expected. A view field that Odoo 17 insists on declaring. An API key function with a different signature. A cron job with no failure counter, which a performance check depended on. Each one turned up in an install or a test, not in a customer's database.

What I have not tested

  • The AI migration itself. It needs a provider key and a running queue.
  • A real S3 bucket. The tests use a fake one.
  • Odoo Enterprise, and a real browser session on the Odoo 17 builds.
